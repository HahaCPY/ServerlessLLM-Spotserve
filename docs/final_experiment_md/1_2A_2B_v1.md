# MoE × SpotServe 實驗結果

日期：2026-09-12（Asia/Taipei）。正式矩陣約於 12:09–14:52 執行。

## 結果摘要與證據範圍

完成 **8 種 configuration × 3 次 = 24 次**正式執行；24 次均在第一次 attempt 通過，沒有排除任何效能較差的有效 run。48 個請求都產生完整 512-token 輸出，且接續後 token 序列與當次 uninterrupted reference 完全相同。

本次沒有證明 MoE-specific optimization 有明顯額外效能收益：MoE SpotServe 的完整 harness runtime speedup 為 **1.0021×**；Migration ablation 為 **0.9996×**；Reparallelization ablation 為 **0.9913×**。這是保留真實結果後的結論，不是依預期挑選樣本。

這份資料是固定 source/target、單次通知式 preemption 的受控 recovery benchmark，**不是完整生產服務的多次 spot-churn 實驗，也沒有實體 expert-weight migration 或 TP configuration 改變**。現有計時與 block counter 也有下述限制；因此不能用本次資料宣稱純 GPU recovery、實際搬移 bytes 或 steady-state serving 的改善。

### Workload、reference 與 preemption

使用既有工程文件作為自然文字 workload，經 checkpoint tokenizer 本機編碼，必要時重複本文，再精確截為 4096 tokens；不是連續人工 token ID。兩個 workload 的 token SHA-256 在 24 次執行均相同：

| Workload | Token-ID SHA-256 |
| --- | --- |
| `docs/spotserve-moe-aware-planner.md` | `057b5c61f60aa329385ffa83fcc305d1b458412590d6420340b1a02751cd6349` |
| `docs/four_version_recovery_comparison.md` | `d4817251165252a4aa908b39230e4168add283ee3bad14d430f40a65077ff4b5` |

每 run 先在 source 產生相同 workload 的 uninterrupted reference，再送出測量請求。prefix caching 關閉，reference 不提供可重用 KV。兩個請求達到 threshold 後，freeze EngineCore（keep requests/cache），取得各自的精確 internal-request snapshot；source prefix 保留完整已產生 output，transferable KV boundary 另由 `computed_tokens` 記錄。

完整輸出 reference hash 在所有 run 均一致：request 0=`017239546ed78745e7758c530e680a7344f7536d06c1452ffe39f06712987cd7`；request 1=`6c2f45c591001bd77d0795dbc3690fc5c3a33602761d3c7799a7ddc66d05f8d1`。

沿用 [四卡 availability trace](../examples/spotserve/spot_trace_qwen15_moe_a27b_batch_recovery.jsonl)：先 add GPU 0–1、再 add GPU 2、3，首次 remove 同時移除 GPU 0–1，target 剩 GPU 2–3。harness 以 1000× speedup 回放到首次 source remove 即返回；**trace 後續的 add/remove 沒有執行**，每 run 僅一次 preemption。事件在 decode 邊界閘門後回放，並非真實等待 180 秒後 hard-kill。

Migration source 需保留至 consumer 拉取/生成完成，因為 NIXL export 是 producer-owned lease；這代表通知/grace-period recovery，不是無預警硬故障。token-replay 策略則先關閉 source 再使用已 ready target。

選擇較大的 Qwen 與 4K context，是為了保留實際 MoE workload 和長 context 恢復成本；Tiny 只用於流程閘門。固定兩端、同一邊界有利公平 ablation，但也限制可選的 placement/configuration，不能保證 MoE 优化必然受益。

### MoE routing 的可觀測性限制

此版 vLLM 明確拒絕 `enable_return_routed_experts` 與任何 KV connector 同時啟用。本次沒有繞過該安全檢查。

先完成 Qwen 的 non-connector live-routing canary，得到兩個請求各 1440 個 layer/expert 組合、418176 / 417888 次 top-k assignments（合計 836064）。校準邊界為 261/258，與所有正式 run 相同。

校準 artifact：[qwen-route-profile.json](../results/moe_spotserve_qwen_a27b_4k_v2/calibration/qwen-route-profile.json)，SHA-256=`006cb7a2c7a8d4455ecc44ff2323bb92541ce6821ade9240837fb8a31c9839a8`。

Non-migration 正式 run 從 source 讀取當次 live top-k buffer；target 不啟用 capture，避免污染 recovery。NIXL run 只在 prompt hash 相符時使用上述真實 calibration，明確標記 `vllm_runtime_topk_calibration`；**不是同次 NIXL live capture，也不是人工 hotness fixture**。calibration 與 NIXL canary、舊 pilot 均未加入 24-run 統計。

### Metrics 的實際定義與限制

表中時間單位為秒，throughput 為 token/s；平均值及 sample standard deviation（n−1）均來自三次有效 run。

| 名稱 | 本次 harness 的實際定義 |
| --- | --- |
| Runtime | `elapsed_s`：容器/網路 setup、兩端 cold startup、reference、測量請求、recovery 與 cleanup 的完整 elapsed time；不是僅 workload completion time |
| Recovery | `recovery_s`：首次 source remove 後至 harness 恢復流程結束；**包含 source shutdown/cleanup**。baseline cleanup 在 target submit 前，NIXL cleanup 在 target final output 後 |
| Downtime | remove 後至 host 收到兩個請求首個 target output；freeze/snapshot 的前置時間不在 remove-clock 內，亦有 control-message 接收成本 |
| Avg/P99 latency | target `generate_started` 後，由 host 觀測首 output 的延遲；**不包含 baseline submit 前的 source shutdown**。每 run 只有兩個樣本，nearest-rank P99 即較慢樣本，不能當 production tail percentile |
| Throughput | 剩餘產生的 505 tokens / `recovery_s`；不是全程或 steady-state tokens/s，受上述 cleanup 定義影響 |
| Migration | export 開始到兩個 target 首 output 的流程時間，含 export、planner、restore staging、拉取與首 token；不是純網路 KV transfer time |
| Repara* | `reparallelization_s` = fresh target startup + planner time；target startup 發生在 preemption 前，**不是 event-triggered configuration-transition time** |
| Repara planner | `reparallelization_planner_s`：原始/MoE-aware planner 的實際呼叫時間 |
| KV blocks / recompute | `restored_blocks` 加總的是 restore staging 回報的 **expected blocks**；`recomputed_tokens` 是 prefix 與 exported computed-boundary 的 metadata 差值，不是 GPU recompute profiler counter |
| Success / correctness | 每 run 兩個 target 都完成剩餘 token budget、finish_reason=`length`，拼接 source output + target suffix 和 reference 逐 token 相同 |

本次未獨立收集 final-output emission timestamp、NIXL 實際 transferred bytes/block acknowledgement、TPOT 或 steady-state throughput。不能從現有 JSON 無損移除 cleanup 成本；**本報告不事後修補或估算 raw timings**。`target_recovery_s` 在 NIXL 模式亦可能涵蓋 source cleanup，不視為純 target compute 指標。

## 4. Analysis

### Experiment 1

依完整 harness runtime 排名為 Reparallelization ≈ Rerouting < MoE SpotServe ≈ SpotServe；replay 兩組相差不到 1 秒，三次波動重疊，沒有明顯 Reparallelization 收益。兩組都只能選 TP=2 / GPU 2–3，並未重新調整 TP/PP/DP/EP，差別主要是 planner overhead。

按記錄的 downtime，SpotServe 比 Rerouting 減少約 **50.515%**，MoE SpotServe 比 Rerouting 減少約 **48.867%**；但不能全部歸因於 KV reuse：baseline 在 target submit 前做 source shutdown，NIXL 為保留 lease 而延後 shutdown，兩者的首 token 關鍵路徑不一致。

反過來，NIXL 的 shutdown 發生在 target final output 後，仍被 `recovery_s` 算入，因此 recorded recovery 較高也不能解讀為 target 純推論較慢。兩種指標與 throughput 都受現有生命週期/計時定義影響。本次證明的是受控請求接續正確與 planner 路徑可執行，不是無混雜的 end-to-end 效能排名。

原始 SpotServe 與 MoE SpotServe 採相同 NIXL 生命週期，較適合做直接 ablation；其 runtime 僅相差 0.856 秒（0.207%），recorded recovery 未改善。本次沒有足夠證據宣稱 MoE-specific optimization 整體有效。

### Experiment 2：為何沒有呈現預期優化

Migration 的 MoE planner 確實看見 calibration histogram：available request=2、target placement=1、logical locality ratio=1.0、remote-routing estimate=0、expert-dispatch cost=0。**固定唯一 target 已涵蓋全部 1440 experts，所以開 expert-locality scoring 不會改變任何 target 選擇。** Original/MoE 使用相同 KV lease 與 transfer payload，沒有實際 expert weight 搬移；flow 差異主要是 planner 與當次流程波動，MoE Migration 未比 Original 快。

Reparallelization 的 candidate_count=1；MoE planner 產生涵蓋 1440 experts 的 logical placement，但 `physical_weight_migration=false`、movement observation unavailable、1440 experts 的 movement 標記 unknown，EP disabled。因為没有可比較配置或可驗證的重量移動，新增 logical plan 建構只呈現額外 planner 成本，沒有後續 placement/parallelism 收益可抵銷。

因此本次不能說 migration optimization 或 reparallelization optimization 對整體 speedup 有明顯貢獻。Migration ablation 接近零收益；Repara ablation 有可見 planner overhead。**模型變大/內容變長本身不會解決「只有一個候選 target/config」或「沒有 physical expert-placement actuation」的限制。**

### 下次正式效能驗證的必要修正（本次未執行）

- 用 preemption notice、首 token 與 final-output emission 的一致時間戳計時，把 freeze/snapshot、source cleanup、target provisioning 分開；保留本次 raw，不事後估算扣除。
- baseline/NIXL 在 recovery 測量期間採一致的 notice/grace lifecycle，避免 source shutdown 先後順序改變首 token 關鍵路徑；hard-kill 另做一組失敗/回退測試。
- 記錄 target KV cached/externally loaded tokens、connector transfer completion 與 bytes，將 staged expected blocks 和實際 reuse 分開；另量 TPOT/steady-state throughput。
- 維持固定 logical source/target 的公平比較，同時提供真正可區分的 expert placements/config candidates；先證明 apply/verify runtime hook 與實體 actuation 可用，再測 MoE placement/movement 收益。
- 完整回放多次 churn 需要額外可重用 capacity/recovery 狀態機與驗證，不能把本次首次 remove 後未執行的 trace events 當成已完成壓力測試。
