# Smaller MoE × dynamic EP SpotServe: experiment protocol

Date: 2026-09-15 (Asia/Taipei). Status: protocol plus native candidate canaries; no Original/MoE-aware A/B or recovery-performance result.

## Why the v1 result is not an EP/dynamic-configuration experiment

The Qwen1.5-MoE-A2.7B v1 source was fixed to GPU0/1 and the target to GPU2/3. Both engines used TP2, DP1, PP1 and EP disabled. After removing GPU0/1, the harness had one target and one legal TP2 configuration. Its MoE-aware planner could construct logical expert metadata but could not choose a different physical placement or parallel shape. Thus v1 established request-continuation correctness under its lifecycle; it did not measure EP or dynamic configuration benefits.

## Model and scope

Use the local, original BF16 `granite-3.1-3b-a800m-instruct` checkpoint at revision `a02780686e08a03fe0d2679a293b5c74a90efa89` for both versions. Its two safetensors shards total 6,597,622,168 bytes, smaller than the v1 Qwen checkpoint. It is a real `GraniteMoeForCausalLM`: 32 MoE layers, 40 experts per layer, top-k 8. Native EP2 has already been observed to place experts 0–19 and 20–39 on different ranks and to complete inference. The current BF16 whole-model correctness gate is **not passed** because repeated-token stress cases diverge across TP/EP shapes. No formal EP performance benefit may be claimed until this gate is resolved. The 318 MB `Qwen2-MoE-Tiny` local checkpoint has only two layers and a 512-token context; use it only for a harness smoke test.

Use four physical RTX 5070 Ti GPUs. Preserve the existing baseline GPU process. Each run checks process ownership, free memory and utilization before creating only experiment-owned containers; only those containers are stopped afterward. Keep checkpoint revision, dtype, vLLM/Torch/CUDA versions, MoE backend, cache identity, scheduler, prompt hashes and GPU UUIDs in every artifact. Do not reuse the v1 raw tree.

## Availability scenarios and the candidate universe

The host has **four** physical GPUs. The earlier `{1,2}`, `{1,3}`, `{2,3}` list came from one deliberately narrow availability event: an initial **real EP2** source on GPU0/1, then GPU0 removed. At that instant, GPU1/2/3 remain schedulable, so the first recovery has three GPUs, not four. A surviving GPU1 rank is not a complete model: each layer has lost half the experts. The experiment must also register separate two- and four-available-GPU states, for example a second removal and a later add-back; these are distinct workload/resource cells, not extra repeats of the three-GPU cell. A four-GPU state after GPU0 returns must be labelled *return/warm-state*, not counted as if the first removal left four cards.

The source freezes at an exact synchronous C1 boundary before the graceful notice, records client-delivered tokens and live routes, and is closed as an experiment-owned **whole group** before any replacement group overlaps GPU1. No live rank join, physical expert-weight migration or arbitrary expert placement is assumed.

For one vLLM group with PP=1 and one replica, the preliminary GPU count is `TP × DP`; enabling EP makes the effective expert group size `TP × DP`. The table below is a **screening universe**, not a list of proven deployment shapes. Every shape requires native startup, real expert ownership, memory/context fit, output correctness, recoverability and matched cost calibration before it becomes a common Original/MoE-aware planner candidate.

| --- | --- | --- |

Granite has 40 experts per layer. The pinned expert-map code divides them unevenly across three EP ranks **when EPLB is off**; a new native GPU1/2/3 canary verified actual 14/13/13 ownership and a complete ordinary request. This does not certify EP3 recovery, repeated service cost or whole-model correctness. EPLB itself requires even expert division and Granite's model↔EPLB interface has already failed a runtime gate, so this protocol does not treat elastic EP as a usable candidate. Merely reversing the Podman `--device` list on GPU1/2 did **not** change rank ownership; explicitly setting `CUDA_VISIBLE_DEVICES=1,0` did swap the physical EP rank ownership in a separate TP2/EP2 canary. Each proposed ordered pair still needs runtime UUID/expert-map verification and matched cost trials.

All shortlisted EP branches must have **effective EP size >1**, not simply `enable_expert_parallel=True` on TP1/DP1. The user's requested three comparisons are **EP-only**: both versions draw from the same verified native-EP candidate set. Calibrate non-EP controls (`TP1` full replicas and `TP2` without EP) separately because prior normal-workload measurements often favoured full replicas. If an unconstrained *overall deployment optimum* comparison is added later, both planners must also be allowed to choose those common non-EP controls; the EP-only result cannot claim the best SpotServe choice among all legal shapes.

The candidate *set* is preregistered and identical across versions; the **selected configuration is not fixed**. Only the selected group/fleet is provisioned after the event. With four cards, one disjoint EP2 source plus two disjoint, simultaneously ready EP2 targets would require six cards. Overlapping target groups are therefore alternatives, not three warm independent targets. The measured notice-to-ready time includes group construction. If both planners choose the same candidate, retain the valid null result; never alter weights or workloads to force a difference.

## What has actually been measured

`TP2/DP1/EP2` and `TP1/DP2/EP2` passed prior native placement/inference probes on **GPU2/3**: each EP rank held 20 disjoint complete experts per Granite MoE layer. Existing warmed batch and capacity measurements cover ordinary and diagnostic shapes on that same pair, with one engine per configuration and repeated batches. For example, the normal prompt512/output128/C8 generated-token throughput was 262 versus 243 token/s; normal prompt4096/output32/C48 was 249 versus 292 token/s. These values do not establish a repeatable EP advantage, and some cross-shape stress outputs still diverge.

New single native canaries—not Original/MoE-aware runs—are preserved in [EP3 report](../../results/moe_dynamic_ep_shape_screen_20260915_attempt1/tp1-dp3-ep3.json), [GPU1/2 EP2 reports](../../results/moe_dynamic_ep_shape_screen_20260915_attempt2/summary.json), and [explicit rank-swap report](../../results/moe_dynamic_ep_shape_screen_20260915_attempt3/tp2-dp1-ep2-12-swap.json). EP3 on GPU1/2/3 passed 32-layer complete 14/13/13 coverage, checkpoint scalar samples and a 32-token request. Both EP2 native shapes passed the same checks on GPU1/2; reversing only the device argument left ownership unchanged, while explicit CUDA ordering exchanged GPU1/2 ownership and preserved the output hash. The first EP3 request incurred cold JIT, so its 110.7-second request wall time is **not warmed serving cost**. The EP2 single cache-hit `engine_ready_s` observations of about 31–36 seconds are **not three independent configuration-transition measurements**.

**No new-source GPU0/1 EP freeze, no calibrated repeated GPU1/2 or GPU1/3 group cost, no EP4 startup, and no EP-group notice-to-ready recovery cost has been measured.** GPU0 acquired about 3.7 GiB of non-experiment occupancy during the EP3 run; four-GPU EP4 canaries are deferred while that occupancy remains. The previously reported roughly 31-second cache-hit recovery measured a TP1 non-EP engine, not an EP2/EP4 switch.

## Recovery method and scope of the migration claim

The default design is host token handoff followed by target GPU prefill and remaining-token replay. The client-delivered source prefix and internally computed prefix are recorded separately; unconsumed tokens are backfilled exactly once. This supports routed-expert capture without combining it with a KV connector and allows EP shapes to change. It does **not** measure NIXL bytes, direct KV restore, less expert-weight movement, or v1's NIXL migration operation. Both versions use the identical handoff/replay implementation, so the ablations isolate planner decisions under that recovery policy.

If direct NIXL KV restore is required, first run a separate source/target TP2/EP2 connector canary and independently verify transferred bytes, KV loaded-token acknowledgements, source lease lifetime and resumed output. Do not label host replay as direct KV migration. A connector failure or lack of a transferable source lease may make the four-GPU dynamic EP candidate set infeasible; report that rather than substituting an unverified restore path.

## Calibrations and MoE signal

Use ordinary tokenizer-encoded text prompts, not repeated-token prompts chosen to bias routing. Split calibration, held-out validation and formal prompts before timing. The primary recovery cell is 4096 input + 512 output tokens, C1, source freeze at exactly 256, then 256 remaining output tokens. A separate short-context cell can use 512 input + 128 output tokens with a preregistered 64-token freeze; treat it as a different scenario, never as another repeat of the primary cell. Higher C is exploratory until a native all-request freeze barrier and matched remaining-work cost calibration pass.

For every legal pair/shape, obtain at least three independent fresh-engine ready/recovery trials under the same cache-hit policy, plus matched remaining-service measurements. Record ready, host install, prefill, TTFT, remaining decode, final output and source cleanup separately. Calibration must measure real GPU UUIDs, expert ownership/coverage, rank kernel/dispatch load, GPU memory/KV capacity and queue status. All candidates must fit the intended context. Compile each required shape before comparable cache-hit timing; retain separate all-cold data instead of mixing compiler misses with hit trials.

Original is the new EP-capable SpotServe baseline with the same physical candidates, verified executor, generic measured costs and completion-time objective; it ignores source routing as a decision input. MoE-aware receives the same inputs plus a **live source expert histogram** and a rank/dispatch cost correction learned from independent candidate runs. A simple full-expert coverage score is excluded because all legal groups cover all 40 experts per layer and it cannot distinguish them. Validate the correction against generic-only and shuffled-routing predictors on held-out prompts before interpreting any decision as MoE-specific. The label “Original” does not mean an unmodified historical v1 binary or a dense model.

## Gates before formal A/B

1. **Resource and runtime:** verify all four physical GPUs can run experiment-owned groups, then inspect real TP/DP/EP values, GPU UUIDs, local expert tensors and per-layer 0–39 coverage for each candidate. Extend the existing TP-only GPU adapter and measured planning bridge; both currently reject EP or DP2. Prior GPU2/3 EP2 serving evidence does not validate the new adapter, other pairs or recovery. A static capability catalogue entry alone is insufficient; add each missing EP3/EP4/replica shape only after its own native runtime canary.
2. **Correctness:** for the same checkpoint and prompts, preserve exact delivered source prefix, compare complete uninterrupted and resumed sequences, and check router/top-k, native collective/expert numerical conservation and repeated-token stress cases. The existing EP stress divergence must be diagnosed or bounded by a preregistered numerical criterion. If unresolved, the GPU matrix may be recorded as exploratory path/cost data, not a formal correct-EP speedup claim.
3. **Capture and barrier:** demonstrate live per-request routing on the EP2 source; demonstrate exact freeze with overshoot 0 and no later source output; verify target receipt of the precise token prefix. C>1 remains gated by a separate all-request barrier test.
4. **Decision evidence:** reject missing or mismatched revision, GPU pair, workload, cache/warm state, transition timing or routing calibration; log candidate count and all cost terms. Generic, true-routing and shuffled-routing predictors use the same candidate set.
5. **Pilot:** one recovery pilot for every shortlisted placement/shape/fleet candidate, then preregister the overall availability trace. The overall comparison uses at least two fixed wall-clock availability events; the second event is set from pilots **before** formal runs and does not move with either version's selected plan. Report which events actually affect the deployed group.

## Formal runs, statistics and artifacts

For each registered scenario in which all three comparisons have at least two passing candidates, run **Original and MoE-aware, three independent fresh-engine runs per version** (minimum 18 runs for that scenario). Cells with fewer eligible candidates are reported as gated or N/A and are not counted as completed ablations. Interleave order `O→M`, `M→O`, `O→M`, reset the initial source group and cache policy, and preserve every failure, attempt and retry. Do not exclude a valid slow run. The two ablations require matching prompt hashes, delivered/frozen boundaries, remaining length and background conditions; a mismatch invalidates the pair but remains in the raw log.

For 2A and 2B, the primary objective is client-observed notice → complete remaining output, including selected target construction and replay. For the overall two-event stream, the primary objective is stream completion time from the fixed arrival-trace epoch; each effective event also has its own notice → first/final recovered-token time. Report notice→freeze, freeze→ready, first resumed token, final token, downtime, per-request TTFT/TPOT/latency, p95 only with an adequate request sample, throughput, GPU/KV occupancy, selected pair/shape, candidate scores and decision-change rate. Report mean ± sample SD, paired differences and uncertainty separately for 1, 2A and 2B. Distinguish planner time, full recovery time and warmed serving time. Do not count setup/reference or source cleanup as hidden components of a named migration/reconfiguration operation.

Write a new dated protocol, raw JSON/logs, schedule, attempts, calibration/canary/pilot artifacts and generated Markdown report in a new results directory. Link each number to run IDs and clock definitions. Leave v1 and Granite v2 results unchanged. A failed gate or same-choice/same-performance result is an explicit negative result, not an invitation to change the candidate set after formal measurement.
